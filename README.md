# Прибор / Контент

Небольшой AI-помощник для подготовки B2B-карточек контрольно-измерительных приборов.
Из входного JSON получает SEO-текст, поисковые запросы и блок для менеджера.
Характеристики переносит из исходных данных, а пробелы отмечает явно.

**Python 3.11 · FastAPI · PostgreSQL 16 · SQLAlchemy 2 · Docker Compose**

## Быстрый старт

```bash
# В рабочей папке .env уже создан. После клонирования создайте его из примера:
cp -n .env.example .env
docker compose up --build -d
```

- Редактор: http://localhost:8080
- Swagger: http://localhost:8080/docs
- Проверка приложения и БД: http://localhost:8080/health

Выберите **testo 510** или **testo 511** и нажмите
**«Открыть сохранённый результат примера»**. Ответ пройдёт проверки, запишется
в PostgreSQL и появится в истории. Это воспроизведение готового ответа ChatGPT,
а не новая генерация. API-ключ не нужен.

Загрузить оба примера без браузера:

```bash
docker compose exec app python -m app.demo --url http://localhost:8000
```

Повторный запуск создаёт новые задания. Данные сохраняются в Docker volume.
Остановка без удаления данных: `docker compose down`.

## Два способа работы с моделью

| Режим | Как работает | Что требуется |
| --- | --- | --- |
| `manual` — по умолчанию | Создать задание → экспортировать промпт и схему → обработать в ChatGPT → импортировать JSON → проверить и сохранить | Доступ к ChatGPT; ручной перенос ответа или агент с доступом к проекту |
| `openai` | Создать задание → OpenAI Responses API со Structured Outputs → проверить и сохранить | `OPENAI_API_KEY` и доступ к выбранной модели |

**Чат ChatGPT не является вызываемой из Python локальной моделью.** Режим `manual`
делает участие человека/агента явным; фоновой генерации после закрытия чата нет.
Оба режима используют одинаковые исходные данные, промпт, схему ответа и проверки.
Разные модели и интерфейсы могут давать разные формулировки.

В тестовом задании требуется LLM API. Он реализован отдельным рабочим адаптером;
ручной режим удобен для демонстрации без ключа, но не заменяет проверку настоящего
API-вызова перед сдачей, если проверяющему важно увидеть именно его.

### ChatGPT без ключа

1. Вставьте JSON товара или выберите пример.
2. Нажмите **«Подготовить запрос»**.
3. Скопируйте запрос в ChatGPT. Он содержит инструкции, исходные данные,
   JSON Schema, ID задания и хеш входа.
4. Попросите вернуть объект `{ "draft_id": "…", "input_hash": "…", "content": {…} }`.
5. Вставьте ответ или загрузите JSON-файл, затем нажмите **«Проверить и сохранить»**.

Неправильный ответ не завершает задание: его можно исправить и импортировать снова.
Готовую карточку перезаписать нельзя; для новой версии создаётся новое задание.
В `work/` можно хранить временные запросы и ответы, эта папка исключена из Git.

CLI для агента или разработчика с установленными зависимостями:

```bash
python -m app.cli create examples/testo-510.input.json
python -m app.cli export <ID_ИЗ_ОТВЕТА> --output work/request.json
# ChatGPT читает request.json и записывает ответ по схеме в work/answer.json.
python -m app.cli complete work/answer.json
python -m app.cli list
```

CLI обращается к HTTP API, а не пишет в таблицы напрямую. Если изменён порт,
передайте `--url http://localhost:НОВЫЙ_ПОРТ` перед именем команды.

### OpenAI API

В `.env` заполните:

```dotenv
OPENAI_API_KEY=ваш_ключ
OPENAI_MODEL=gpt-4.1-mini
DEFAULT_PROVIDER=openai
```

Пересоздайте контейнер приложения:

```bash
docker compose up -d --force-recreate app
```

Выберите OpenAI API в редакторе. SDK использует Responses API, строгую JSON Schema,
`store=False`, тайм-аут и не более одного автоматического повтора транспортных ошибок.
Лимит, тайм-аут, отказ модели, неверный ответ и ошибки подключения возвращаются
как понятные ошибки. Секреты и исходный текст ошибок провайдера не возвращаются клиенту.
Собственный ключ нужен только для этого режима; фиктивный ключ в проект не встроен.

## Вход и выход

```json
{
  "name": "testo 510 дифференциальный манометр",
  "manufacturer": "Testo",
  "specs": {
    "тип прибора": "дифференциальный манометр",
    "артикул": "0563 0510"
  },
  "description": "",
  "expected_specs": ["диапазон измерений", "точность", "питание"]
}
```

`name` обязателен. Остальные данные могут отсутствовать. Значения `specs` — строки
или `null`: так не теряются единицы, десятичные запятые и ведущие нули в артикулах.
Числа без единиц автоматически не преобразуются. `expected_specs` задаёт список
параметров для проверки, его можно адаптировать под категорию прибора.

Пустое поле или `null` превращается в «данных нет». Поля из `expected_specs`,
которых нет в `specs`, требуют уточнения. Проверка полноты относится к структурированным
полям: если значение есть только в паспорте, перенесите его в `specs` после проверки.
Из текста паспорта автоматически не извлекаются характеристики для таблицы.

Результат содержит:

- `seo_title`: не более 70 символов;
- `seo_description`: 800–1200 символов с пробелами и переводами строк;
- `characteristics`: список характеристик, собранный Python;
- `search_queries`: 3–5 разных запросов;
- `commercial_block`: краткий блок для менеджера;
- `missing_fields`, `warnings`, `review_required`: что нужно проверить;
- `evidence`: точные цитаты исходных полей, выбранные моделью.

Два примера из предоставленной выгрузки:

| Товар | Исходные данные | Готовый Markdown | Готовый JSON |
| --- | --- | --- | --- |
| testo 510 | [input](examples/testo-510.input.json) | [карточка](examples/testo-510.md) | [result](examples/testo-510.result.json) |
| testo 511 | [input](examples/testo-511.input.json) | [карточка](examples/testo-511.md) | [result](examples/testo-511.result.json) |

[Происхождение данных и ограничение полноты](examples/SOURCES.md).
Ни диапазоны, ни точность из внешних источников не подставлялись. Готовые тексты
созданы ChatGPT по экспортированным заданиям и затем импортированы через API.

## API

| Метод | Путь | Назначение |
| --- | --- | --- |
| POST | `/api/drafts` | Создать задание: `{product, provider}` |
| GET | `/api/drafts?limit=20&offset=0` | История заданий |
| GET | `/api/drafts/{id}` | Исходные данные, статус, результат и сведения о модели |
| GET | `/api/drafts/{id}/request` | Промпт и схема для ChatGPT |
| POST | `/api/drafts/{id}/result` | Проверить и импортировать ручной ответ |
| GET | `/api/drafts/{id}/markdown` | Карточка для копирования |
| GET | `/health` | Проверка соединения с БД |

Пример создания задания:

```bash
curl -sS http://localhost:8080/api/drafts \
  -H 'Content-Type: application/json' \
  -d '{"provider":"manual","product":{"name":"Манометр","specs":{}}}'
```

Ошибки: `422` — некорректные данные; `404` — задание не найдено;
`409` — неправильное задание, повторный импорт или результат ещё не готов;
`429` — лимит провайдера; `502` — ошибка/невалидный ответ модели;
`503` — нет ключа или недоступна БД; `504` — тайм-аут модели.

## Устройство и решения

| Модуль | Ответственность |
| --- | --- |
| `schemas.py` | Строгие схемы входа, ответа модели и импорта |
| `prompts.py` | Версионированный промпт, одинаковый для обоих режимов |
| `providers.py` | Единственный внешний LLM-адаптер: OpenAI |
| `validation.py` | Проверка цитат и чисел, сбор характеристик и пропусков |
| `database.py` | Одна таблица заданий: вход, источник, результат, статус, ошибка |
| `main.py` | HTTP-сценарии и переходы `pending → completed / failed` |
| `export.py` | Безопасное преобразование карточки в Markdown |
| `cli.py`, `demo.py` | Обмен с ChatGPT и воспроизведение сохранённых примеров |
| `static/` | Редактор без сборщика и внешних CDN |

Промпт ограничивает модель исходными фактами, запрещает расшифровывать артикулы
по памяти, задаёт стиль B2B и просит приводить цитаты. Вход передаётся отдельным
сообщением как данные. Инструкции внутри описания не должны исполняться.

Код дополнительно проверяет длины, структуру, уникальность запросов, существование
цитат и появление новых числовых токенов. Для распространённых единиц проверяется
сочетание числа с единицей: наличие номера модели во входе не разрешает приписать
ему единицу давления. Эти проверки намеренно консервативны, преобразование единиц
и запись чисел в другом формате могут быть отклонены.

Характеристики никогда не берутся из ответа модели. При ручном импорте сверяются
ID и SHA-256 нормализованного входа. Сохранение выполняется условным SQL UPDATE:
два одновременных импорта не смогут перезаписать готовую карточку.

PostgreSQL добавлен для истории и устойчивого обмена заданиями по запросу пользователя.
Для этого MVP не нужны Celery, Redis, авторизация, CMS, RAG или векторная БД.
Таблица создаётся при первом запуске через `create_all`; приложение запускается
одним worker. Для последующих изменений схемы потребуется Alembic.

## Настройки и проверки

Все настройки находятся в `.env`; [.env.example](.env.example) содержит безопасные
демонстрационные значения. `.env` исключён из Git и Docker build context.
`DATABASE_URL` в Docker указывает на хост `db`; при локальном запуске задайте URL
вашего PostgreSQL. Пароль в URL и `POSTGRES_PASSWORD` должны совпадать.
`APP_PORT` меняет внешний порт; `OPENAI_TIMEOUT_SECONDS` — тайм-аут API.

Версии зависимостей закреплены в `requirements.lock` и `requirements-dev.lock`.
`pyproject.toml` описывает прямые зависимости и настройки инструментов.

```bash
python3.11 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-dev.lock
python -m pytest -q
ruff check app tests
ruff format --check app tests
docker compose config --quiet
```

Если окружение создано через `uv` без pip, используйте
`uv pip install -r requirements-dev.lock`.

Тесты не требуют ключа и запущенного PostgreSQL: используют временную SQLite.
Проверяются полный ручной цикл, сохранение после перезапуска, формат и полнота,
подмена задания, повторный импорт, выдуманные числа, а также настоящий OpenAI SDK
с `httpx.MockTransport`: строгий формат запроса, разбор ответа, ошибки, отказ и тайм-аут.

**Проверено при подготовке:** 47 тестов, Ruff, синтаксис JavaScript и конфигурация
Compose. Примеры прошли полный цикл API с SQLite внутри процесса. Из-за запрета
сокетов в рабочей среде тестовый runner периодически будил asyncio selector;
это временный обход ограничения тестовой среды, не часть кода приложения.
Запуск контейнеров, соединение с PostgreSQL и платный вызов OpenAI здесь не проверены:
Docker-сокет недоступен, создание серверных сокетов запрещено, API-ключ не задан.

## Ограничения и следующий шаг

- Проверка цитаты подтверждает её наличие, но не доказывает все утверждения текста.
  Семантические ошибки и prompt injection полностью не исключены. Нужна редакторская
  проверка; результат всегда помечен как черновик.
- При скудном входе описание в 800–1200 символов содержит вопросы для уточнения,
  а не полноценные преимущества товара. Для публикации нужен паспорт.
- Список ожидаемых характеристик задаётся явно; синонимы автоматически не объединяются.
- Сбой процесса во время API-вызова может оставить `pending`. В MVP создайте новое
  задание; позже можно добавить тайм-аут состояния, восстановление и идемпотентность.
- Нет пользователей, ограничений частоты и защиты публичного сервиса. Compose публикует
  приложение только на `127.0.0.1`, порт PostgreSQL наружу не открыт.
- Здесь нет автоматического парсинга каталога, цен, остатков и публикации в CMS.

После MVP полезны проверка на реальном API и PostgreSQL, дополнительные примеры
с полными паспортами, оценочный набор на галлюцинации и миграции схемы при её развитии.

## Короткое описание для сдачи

Реализован сервис подготовки черновиков товарных карточек на FastAPI с PostgreSQL
и Docker Compose. Добавлены интеграция с OpenAI API и явный режим обмена с ChatGPT
без API-ключа. Характеристики переносятся из источника кодом, недостающие данные
отмечаются, ответы проверяются перед сохранением. Есть веб-редактор, экспорт JSON
и Markdown, два примера из предоставленного каталога и автоматические тесты.
В примерах мало технических данных, поэтому неподтверждённые параметры не добавлялись.
Настоящий вызов OpenAI без ключа не выполнялся.
